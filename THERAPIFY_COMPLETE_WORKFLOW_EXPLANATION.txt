1. WHAT THERAPIFY ACTUALLY IS
===========================
Therapify is a mental wellness web application. A person can create an account, sign in, record a mood, keep journal entries, chat with an emotional-support companion, answer an age-specific questionnaire, explore wellness activities, request personalized recommendations, and discover or enroll in events.

The MERN letters describe four layers:
  M - MongoDB: stores documents such as users and journal entries.
  E - Express: receives API requests and decides which backend code handles them.
  R - React: creates the pages, forms, charts, dialogs, and interactive controls.
  N - Node.js: runs JavaScript on the server, outside the browser.

Atlas is the hosted MongoDB deployment used by this project. Atlas does not replace Express. Express applies authentication and application rules before asking MongoDB to read or write a document.

The implemented product is an emotional-support and self-reflection application. The source has no trained diagnostic model, clinical assessment engine, therapist appointment system, or automatic emergency dispatch. A list of condition names in backend/config/mentalHealthTopics.js is vocabulary for scope matching, not a list of diseases the application can diagnose.

Implemented modules and principal files:
  Accounts: frontend/src/pages/Register.jsx, SignIn.jsx; backend/routes/authRoutes.js.
  Shared navigation: frontend/src/app/Root.jsx.
  Landing experience: frontend/src/pages/Home.jsx and LandingLayout.jsx.
  Dashboard: frontend/src/pages/Dashboard.jsx.
  Moods: frontend/src/pages/Mood.jsx; backend/routes/moodRoutes.js.
  Questionnaire: frontend/src/app/components/AdaptiveMoodCheckin.jsx; backend/routes/moodCoachRoutes.js.
  Journal: frontend/src/pages/Journal.jsx; backend/routes/journalRoutes.js.
  Chat: frontend/src/pages/Chat.jsx; backend/routes/chatRoutes.js.
  AI generation: backend/services/geminiService.js.
  Wellness: frontend/src/pages/Wellness.jsx; backend/routes/wellnessRoutes.js.
  Personalized recommendations: backend/routes/recommendationRoutes.js.
  Events: frontend/src/pages/Events.jsx; backend/routes/eventRoutes.js.
  Event persistence and payments: backend/services/eventStore.js and eventPayments.js.

2. TECHNICAL VOCABULARY FROM ZERO
===============================
Browser: the program displaying the website. React runs here. Browser code must not contain server secrets.
Frontend: everything responsible for the user's screen and interaction. A button can update screen state without saving anything remotely.
Backend: the server program responsible for trusted decisions, authentication, database access, and calls requiring secret credentials.
API: an agreed way for programs to communicate. In this project the browser calls HTTP URLs and usually exchanges JSON.
Endpoint: one method and URL combination, such as POST /api/moods. GET /api/moods is a different operation even though the URL is the same.
HTTP method: describes the operation. GET reads, POST submits or creates, PUT updates a resource, PATCH updates selected fields, DELETE removes.
JSON: a text representation of data. JSON.stringify converts a JavaScript object to request text. response.json parses response text into a JavaScript value.
Component: a reusable React function that describes some UI. Mood is a page component; Dialog is a reusable UI component.
State: data React remembers between renders. Changing state asks React to render the screen again.
Props: values passed from a parent component to a child. Home passes user and mood handlers to LandingLayout.
Hook: a React function such as useState or useEffect that gives a component state or lifecycle behavior.
Route: a URL mapping. React routes choose pages; Express routes choose request handlers. They are separate systems.
Middleware: a function that runs before an Express handler, for example to verify a token or parse JSON.
Database document: one MongoDB record. A journal entry is one document with fields such as body, title, and user.
Collection: a group of MongoDB documents, roughly comparable to a table conceptually, but documents can contain nested objects and arrays.
Schema: a program-level description of allowed fields and types. Mongoose schemas validate many of this project's document writes.
ObjectId: MongoDB's usual identifier type. In JSON it is commonly represented as a 24-character hexadecimal string.
Reference: an identifier connecting records. Journal.user points to a User identifier; it does not copy the user's whole profile.
CRUD: Create, Read, Update, Delete. Journal supports all four through its route file.
Promise: a value representing a result that will arrive later. Network and database operations return promises.
async/await: syntax for waiting on promises without blocking the Node.js event loop in the way a synchronous busy loop would.
Token: a signed piece of data used to prove login. Here it is a JWT stored in browser localStorage.
Hashing: one-way processing used for passwords and fingerprints. Password hashing is different from encryption.
Encryption: reversible transformation using a secret key. Chat encryption can be reversed by the backend because it has that key.
Cache: temporary reuse of a previous result. Here AI-result caches are in process memory, not a permanent database.
Transaction: several database operations treated as one consistent unit. Event seat allocation uses MongoDB transactions.
Idempotent operation: repeating the operation does not create another logical record. Repeating a successful enrollment returns the existing booking.
LLM: a large language model that generates text from instructions and context. Therapify calls Google's Gemini service; it does not train an LLM.
Prompt: the instructions and input sent to the model. Context is reference information included with that prompt.

3. ARCHITECTURE AND STARTUP
==========================
The current top-level application structure is:
  backend/  - one Express server for all modules, including Events.
  frontend/ - one React application built by Vite.
  shared/   - the shared wellness JSON catalog used by backend services.
There is no separate Events backend in the current architecture.

Conceptual flow:
  User -> React page -> fetch HTTP request -> Express middleware -> route
       -> service/model -> MongoDB Atlas and optionally Gemini or Razorpay
       -> route JSON response -> React state update -> visible result.

Frontend startup:
1. frontend/index.html supplies the root HTML element and loads the application entry.
2. frontend/src/main.jsx imports createRoot from react-dom/client, App, and styles/index.css.
3. createRoot(document.getElementById('root')).render(...) mounts React.
4. frontend/src/app/App.jsx renders RouterProvider with the router from routes.js.
5. routes.js uses createBrowserRouter. Its parent is Root; child routes select pages.
6. Root renders navigation, Outlet, and footer. Outlet is where the current child page appears.
7. Some generated files use _jsx and _jsxs imported from react/jsx-runtime. These are JSX runtime helpers; they serve the same rendering purpose as familiar JSX tags.

Registered browser routes:
  /, /dashboard, /events, /signin, /register, /chat, /mood, /journal,
  /wellness, /careers, /press, /privacy, /terms, /cookies, /crisis, and *.
The final * route shows NotFound. AdaptiveMoodCheckin is imported in routes.js but is not registered as a standalone page route. It is embedded in the mood experience.

Backend startup in backend/server.js:
1. require('dotenv').config() loads backend environment values when started from backend/.
2. getEncryptionKey() validates the required chat encryption key before accepting requests.
3. Express, CORS, route modules, the database connector, and authentication middleware are imported.
4. express() creates the server application.
5. CORS permits the configured hardcoded frontend origin http://localhost:5173, specified methods, and Content-Type/Authorization headers. credentials:true permits credentialed browser requests but does not itself implement cookie login.
6. express.json() parses incoming JSON bodies into req.body.
7. app.use mounts route groups under /api/auth, /api/journals, /api/moods, /api/mood-coach, /api/chat, /api/recommendations, /api/events, and /api/wellness.
8. connectDB() calls mongoose.connect(process.env.MONGO_URI).
9. app.listen executes after connectDB resolves, so the shared Atlas connection is ready before requests arrive.
10. GET / returns a small health message.

Port configuration:
The inspected backend environment sets PORT=5000. server.js falls back to 5001 if PORT is missing. Most frontend API bases fall back to http://localhost:5000. Match frontend VITE_API_URL to the actual backend port. Vite exposes VITE_ variables to browser code, so database credentials and provider secrets must remain backend-only variables.

Vite configuration in frontend/vite.config.js:
  defineConfig organizes the build configuration.
  @vitejs/plugin-react handles React source transformation and development integration.
  @tailwindcss/vite processes Tailwind styling.
  figmaAssetResolver resolves figma:asset/... references to src/assets paths if used.
  The @ alias points to frontend/src.
  assetsInclude allows SVG and CSV asset imports.
This file configures frontend tooling; it is not a backend API server or database proxy.

4. HOW ONE REQUEST TRAVELS THROUGH THE SYSTEM
============================================
Example: saving a journal entry.
1. The user types into controlled inputs in frontend/src/pages/Journal.jsx.
2. onChange handlers update title/body state. At this point text is in browser memory.
3. Clicking Save calls handleSave(). It checks body.trim() and the presence of a login token.
4. fetch sends POST /api/journals, Content-Type: application/json, and Authorization: Bearer <token>. The body contains title, body, mood, tag, and allowAIAnalysis.
5. Express parses the body. authMiddleware verifies the JWT using JWT_SECRET.
6. Middleware sets req.user.userId from the verified token. The browser does not get to choose another owner in the request body.
7. journalRoutes constructs a Journal with user:req.user.userId and normalized fields.
8. If analysis was explicitly enabled, the route attempts optional analysis; otherwise no Gemini analysis is requested.
9. entry.save() validates the Mongoose document and writes it to Atlas.
10. The server returns HTTP 201 with {message, entry}.
11. response.json() gives the browser an object. setEntries and setSelectedEntry update local state.
12. React renders the saved entry detail view. The data survives refresh because Atlas has the record.

Important distinction: a React state update does not prove persistence. The successful backend write is the persistence step. Conversely, an HTTP timeout does not always prove a write failed; the server may have completed it before the browser stopped waiting. This is why repeated booking actions need idempotency.

5. ACCOUNTS, AUTHENTICATION, AND AUTHORIZATION
============================================
Frontend files: frontend/src/pages/Register.jsx and SignIn.jsx.
Backend files: backend/routes/authRoutes.js, backend/middleware/authMiddleware.js, backend/models/User.js.

Registration:
1. Register stores name, email, password, selected goals, step, loading, and error in useState.
2. The first step validates required inputs and an eight-character password minimum in the browser.
3. The second step offers wellness goals. toggle() adds/removes a goal from selected state.
4. handleRegister sends POST /api/auth/signup with name, email, password, and role:'client'.
5. Selected goals are NOT included in that payload and have no field in User.js. They are UI state, not saved personalization.
6. The backend checks required fields and User.findOne({email}) for an existing user.
7. bcrypt.hash(password,10) creates a password hash. The 10 is the bcrypt cost setting.
8. User.create saves name, email, hashed password, and role.
9. The response includes safe profile fields, not the password hash. Registration navigates to /signin; it does not automatically issue a login token.

Sign-in:
1. handleSignIn prevents the form's ordinary browser submission, sets loading, and sends email/password to POST /api/auth/signin.
2. The backend reads User.findOne({email}).
3. bcrypt.compare checks whether the submitted password matches the stored hash.
4. For valid credentials, jwt.sign signs {userId,role} with JWT_SECRET, expiresIn:'7d'.
5. The browser stores token and JSON user data in localStorage.
6. It navigates to a permitted return destination for Dashboard or Events; otherwise it goes to /.
7. Wrong credentials produce 401. Missing required inputs produce 400.

Authentication middleware:
  It reads req.headers.authorization, requires 'Bearer ', splits out the token,
  calls jwt.verify, sets req.user={userId,role}, then calls next().
  Missing, expired, or invalid tokens receive 401.

Authentication means identifying the caller. Authorization means deciding what that caller may access. Most personal routes enforce authorization by querying both the record ID and user:req.user.userId. For example, knowing another journal's ID is insufficient because Journal.findOne({_id:id,user:currentUser}) must also match the owner.

The JWT payload is signed, not confidentially encrypted. Do not place journal text or passwords inside a JWT. localStorage persists across page refreshes and is readable by browser JavaScript running on that origin.

Logout in frontend/src/app/Root.jsx removes token and user from localStorage and navigates to /. There is no backend token revocation endpoint or refresh-token system in the inspected routes. A copied valid JWT can remain valid until expiration.

Current limitations worth understanding:
  The backend signup handler accepts role from the request (within the schema enum). The normal UI sends client, but UI behavior is not a security boundary.
  There is no general role-permission middleware for an implemented admin dashboard.
  Password length checking in the form is stronger than the backend's required-field check; a direct API caller can bypass frontend checks.
  Forgot password is a placeholder link in SignIn, not a working reset flow.
  credentials:'include' in some fetch calls does not turn this Bearer-token design into cookie authentication.

6. HOME PAGE AND DASHBOARD
=========================
Home.jsx is the data/controller component for the landing experience. LandingLayout.jsx renders the active layout with props supplied by Home. Root supplies the outer navigation and footer.

Home behavior:
  Fetches /api/auth/count for the user count.
  Reads the locally stored profile for a greeting.
  For a signed-in user, fetches /api/moods and detects today's entry using a local YYYY-MM-DD date string.
  handleSelectMood builds a mood payload and POSTs /api/moods.
  It updates entries and selectedMood from the saved result.
  It computes week data, averages, trend wording, streaks, and other derived values.
  The actual return passes a specific subset of values to LandingLayout. A calculated value is not necessarily displayed if it is not passed or consumed.

Home's insightMessage is ordinary JavaScript logic based on mood data. It is not a separate Gemini call. For example, averages and changes choose from predefined reflection sentences. This illustrates the difference between computed personalization and generated personalization.

Dashboard.jsx:
1. Reads the token; absent token redirects to /signin with from:'/dashboard'.
2. loadCore uses Promise.allSettled for mood and journal requests, so one failing request need not discard the other successful result.
3. It identifies today's saved mood and note.
4. It keeps only the three newest journal entries for the dashboard panel.
5. loadEvents separately calls /api/events/mine.
6. chartData builds the last seven calendar days and uses null for missing entries.
7. Recharts displays the data; connectNulls:false leaves gaps instead of inventing missing mood values.
8. saveMood sends score, label, emoji, note, local date, and existing emotions to /api/moods.
9. Upcoming bookings are filtered by status/end time, sorted by startsAt, and displayed as a summary.
10. Links such as /journal?new=1, /journal?entry=<id>, /wellness?activity=ground, and /events?tab=mine open specific views.

Dashboard's wellness suggestion is also a local rule: low selected scores choose ground, score 3 chooses movement, and other cases choose gratitude. It is not produced by the recommendation endpoint.

A current inconsistency: Mood.jsx labels score 3 as Good, while Dashboard labels score 3 as Okay. Both save numeric scores on the same 1-5 scale. The numeric data interoperates, but the labels are not uniform. This guide describes the inconsistency rather than pretending it has been fixed.

7. MOOD LOGGING, HISTORY, AND CHARTS
==================================
Files: frontend/src/pages/Mood.jsx; backend/routes/moodRoutes.js; backend/models/Mood.js.

Frontend state tracks selectedMood, selectedEmotions, note, entries, todayEntry, logged, week/month tab, loading, saving, deleting, errors, and success messages.

Saving:
1. Click a face to select its numeric score.
2. toggleEmotion adds/removes labels such as Calm, Anxious, or Tired.
3. Type an optional note.
4. handleLog constructs the payload with getLocalDateStr().
5. POST /api/moods verifies the token and checks that Number(mood) is between 1 and 5.
6. The backend finds a record for that user and dateStr.
7. If found, it changes fields and saves; otherwise Mood.create inserts a record.
8. The browser replaces the same-date item in its local entries array and shows the saved state.

The current handler is a find-then-save/create workflow, not an atomic unique upsert. The compound {user:1,dateStr:1} index exists but is not unique. Two simultaneous first saves for the same date could create duplicates. This is different from the stronger unique enrollment constraint used for Events.

Other operations:
  GET /api/moods reads the user's entries sorted by dateStr and createdAt descending.
  GET /api/moods/date/:dateStr returns one entry or null.
  PUT /api/moods/:id updates specified supported fields with ownership and validators.
  DELETE /api/moods/:id removes the owned record.
  handleDeleteToday confirms, sends DELETE, and clears today's UI state.

Charts:
  Week view computes Monday through Sunday of the current week.
  A Map matches date strings to entries.
  Missing dates become null, not zero: zero is not an allowed mood score.
  Week average includes only existing scores.
  Month view uses four buckets: days 1-7, 8-14, 15-21, and 22-31.
  A bucket average is the sum divided by number of recorded scores, rounded for display.
  These statistics are descriptive arithmetic, not a mental-health diagnosis or model forecast.

Local date strings avoid accidentally changing a person's selected calendar day just because an ISO timestamp is UTC. However, browser local time, server local fallback time, and the 30-day context cutoff's UTC date calculation are not one unified timezone policy.

8. ADAPTIVE MOOD QUESTIONNAIRE
=============================
Files: frontend/src/app/components/AdaptiveMoodCheckin.jsx, backend/routes/moodCoachRoutes.js, backend/models/MoodCheckin.js.

Adaptive here means the question set changes with an age-group selection. It does not mean Gemini invents each next question. The supported groups are 13-18, 19-21, and 22-25. Question definitions exist in frontend and backend. Common themes include feelings, sleep, energy, pressures, relationships/support, the main concern, and the user's immediate goal.

Workflow:
1. A mood record supplies moodEntryId to the component.
2. The component asks for age range and consent before starting.
3. questions=QUESTIONS[ageGroup] selects the fixed set.
4. current=questions[step] selects the current question.
5. updateAnswer creates an updated answers object and calls saveProgress.
6. saveProgress constructs answer IDs/values and currentStep, then queues PUT /api/mood-coach/progress.
7. saveQueue is a useRef holding a Promise chain. New saves wait for earlier saves so an older request is less likely to overwrite a later answer from that browser.
8. previousQuestion and nextQuestion await queued work before moving.
9. On the last step, finishCheckin waits for saving to complete, then POSTs /api/mood-coach/finish.
10. Backend checks consent===true, a valid age group, a valid mood ID, and ownership of the Mood document.
11. It uses server-defined questions/options to normalize answers. Unexpected choices become empty answers.
12. reflect() builds a short response from fixed sentences; recommend() ranks a fixed set of activity categories.
13. It saves questions, reflection, recommendations, and completed:true with findOneAndUpdate and upsert:true.
14. The UI displays the result.

Example: 'Not restful' sleep or a goal of 'Resting' ranks sleep. Feeling overwhelmed, very stressful pressure, or wanting calm ranks grounding and breathing. Low energy or wanting motivation ranks movement. A goal of understanding feelings or talking can rank journaling. Defaults fill remaining choices, and the result is limited to three.

Persistence:
  GET /api/mood-coach/progress/:moodEntryId restores ageGroup, answers, currentStep, completion, reflection, and recommendations.
  PUT /progress stores unfinished progress and rejects editing a completed questionnaire with 409.
  POST /finish returns the existing completed result when applicable.
  The unique {user:1,moodEntry:1} index prevents duplicate check-in records for one person's mood entry.

The six questionnaire recommendation IDs (breathing, grounding, mindfulness, journaling, movement, sleep) are category-like identifiers. They are not identical to the eight exercise IDs in shared/wellnessCatalog.json. Do not assume all such IDs can directly open /wellness?activity=<id> without a mapping.

9. JOURNAL CRUD AND ANALYSIS
===========================
Files: frontend/src/pages/Journal.jsx; backend/routes/journalRoutes.js; backend/models/Journal.js.

The page uses list, editor, and detail states. startNewEntry clears the editor; openEntry selects an existing object; handleSave sends POST for a new entry or PUT for an existing entry; handleDelete requests confirmation and sends DELETE.

Query parameters:
  ?new=1 starts in the editor.
  ?entry=<id> selects the matching item after loading the user's entries.

The model contains user, title, body, mood, tag, allowAIAnalysis, aiAnalysis, isSynthetic, createdAt, and updatedAt. aiAnalysis can contain policyVersion, emotionalPatterns, stressTriggers, positiveDevelopments, recurringConcerns, recommendedExercise, and analyzedAt. Journals are not encrypted by the chat encryption service.

Analysis on creation:
  allowAnalysisInEditor starts false.
  When POST receives allowAIAnalysis===true, it calls generateJournalAnalysis with body, title, and the wellness catalog before saving.
  An analysis failure is caught so a journal can still be saved.
  This creation branch does not apply the same explicit safety precheck and 20,000-character check as the dedicated analyze endpoint. The difference matters when describing protections.

Analysis from detail view:
1. runAIAnalysis checks the UI's detailConsent flag (which initially defaults true in the current code).
2. It POSTs /api/journals/:id/analyze with consent:true and forceRefresh.
3. Backend requires the literal boolean true and reads the owned journal.
4. checkMessageSafety runs on the current journal body before cache lookup.
5. A safety interception returns guidance in analysis fields without asking Gemini.
6. Body length above 20,000 is rejected by this endpoint.
7. analysisCacheKey combines 'scope-v2', entry ID, and a SHA-256 hash of title/body.
8. Without forceRefresh, it can reuse the in-memory cache or a stored analysis with the current policyVersion.
9. Otherwise generateJournalAnalysis calls Gemini (or returns its mock result in mock mode).
10. The result's recommended exercise must match a real catalog ID. The backend supplies its canonical title and local URL.
11. findOneAndUpdate includes the original body, title, and updatedAt in its filter. If the entry changed during generation, the update does not match and returns 409 instead of attaching stale analysis.
12. Success stores the analysis and allowAIAnalysis:true, caches it for 1800 seconds, and returns it.

Editing unsets stored aiAnalysis. The route also calls cache.delete with an older simple key form; the actual content-hashed key prevents edited content from reusing the old-content cache key. Old entries may remain in memory until expiry, so deletion of that older key is not a full cache purge.

Journal output is a reflection on the supplied entry. A field named recurringConcerns does not mean the model analyzed every historical journal. This function receives one journal entry plus the catalog.

10. CHAT INTERFACE AND CONVERSATION LIFECYCLE
============================================
Files: frontend/src/pages/Chat.jsx; frontend/src/app/components/MarkdownRenderer.jsx; backend/routes/chatRoutes.js; backend/models/Conversation.js.

The page separates conversation-list state from active-message state. conversations feeds the sidebar. activeId identifies the saved conversation. messages is the visible message array. input contains unsent text. sendingRef prevents duplicate concurrent sends from the same component. useWellnessContext starts false.

Loading and managing conversations:
  fetchConversations GETs /api/chat/conversations with the Bearer token.
  The backend reads only conversations whose user matches the authenticated caller and sorts newest-updated first.
  It returns title, messageCount, lastMessageSnippet, timestamps, and isSynthetic rather than the entire history for every list item.
  selectConversation GETs /api/chat/conversations/:id and displays that conversation's messages.
  handleNewChat clears activeId and resets to the local welcome message. This UI action alone does not immediately insert a document.
  saveRename PATCHes the ID endpoint. The backend sets the trimmed title and increments __v.
  deleteConversation confirms and DELETEs the ID endpoint, then removes it from local sidebar state.
  There is also an explicit POST /api/chat/conversations API that creates a welcome-message conversation. The normal New Chat handler does not call it.

Sending a message, in exact conceptual order:
1. Clicking Send or a suggestion calls send(text).
2. Empty text and an already-running send are ignored; missing login asks the user to sign in.
3. The frontend optimistically appends the user's message and clears the input.
4. The payload contains message, conversationId, and contextConsent. It does not contain trusted model/system history.
5. POST /api/chat first runs authMiddleware.
6. The route validates message type, non-empty content, maximum 3000 characters, boolean consent, and optional ObjectId format.
7. If an ID is supplied, Conversation.findOne({_id:id,user:userId}) retrieves the owned document. Missing ownership returns 404.
8. The backend constructs history from the stored conversation, initially taking at most 200 messages. Client-supplied history cannot substitute another person's messages or invent a system role.
9. It computes safety and topic scope before the limiter. A 60-request/15-minute per-user limiter applies, with a skip for intercepted safety messages.
10. A new Conversation is prepared if necessary. deriveConversationTitle strips formatting characters and uses a short first-message title.
11. needsAIContext excludes safety interceptions, out-of-scope messages, and plain greetings. Those paths avoid unnecessary profile/wellness context queries.
12. For relevant substantive messages, it fetches the user's name and, only with consent, broader wellness context. Promise.all lets independent reads overlap.
13. generateChatResponse performs the response selection explained below.
14. If the source is unavailable, the route returns 503 without saving a successful-looking reply.
15. Otherwise it appends user and AI messages with flags such as isCrisis, safetyCategory, awaitingSafetyCheck, and outOfScope.
16. conversation.save applies validation, encryption setters/hooks, and optimistic concurrency before writing to Atlas.
17. Response includes reply, flags, conversationId, title, and saved messages.
18. The browser replaces its optimistic messages with the authoritative saved array and updates the sidebar.
19. useEffect scrolls bottomRef into view when messages/loading change.

The response is ordinary request/response JSON, not token streaming over SSE or WebSockets. There is no socket.io integration in these files.

MarkdownRenderer:
  Splits text into lines and constructs React paragraphs, heading elements, unordered/ordered lists, bold, italic, and links.
  renderInline parses supported inline forms.
  It does not use dangerouslySetInnerHTML to inject arbitrary model HTML.
  It is a small custom renderer, not a full CommonMark implementation.
  Links get target='_blank' and rel='noopener noreferrer'; the renderer itself does not implement an explicit protocol allowlist for model-provided URLs.

11. EXACT AI INTEGRATION AND PROMPTS
===================================
Main source: backend/services/geminiService.js.
Retry wrapper: backend/services/geminiRequestService.js.

The SDK is @google/genai. The file imports {GoogleGenAI}. getAIClient lazily constructs a client when generation is required and checks GEMINI_API_KEY. Lazy construction allows local rule/mock branches to run without constructing a live client unnecessarily.

The exact model-selection expression is:
  process.env.GEMINI_MODEL || 'gemini-3.5-flash-lite'
The inspected backend environment sets GEMINI_MODEL to gemini-3.5-flash-lite and AI_MODE to live. A Gemini key is present, but its value is not included here. These are the inspected file settings, not proof of the environment inherited by every previously started process. A running process needs restarting to load changed environment files.

There is no OpenAI SDK call, local model training, TensorFlow model, Python inference server, fine-tuning job, embeddings pipeline, or vector database in the inspected implementation. The model is used through Google's hosted generation API.

Model name vs display name:
  'Therapify AI' is the product persona shown to the user.
  'gemini-3.5-flash-lite' is the configured provider model identifier.
  A model identifier in source does not verify external availability or performance. This documentation did not call the provider to test availability.

Three generation jobs use the same selected model:
A. Chat text: generateAIResponse, used through generateChatResponse.
B. Structured wellness recommendations: generateMoodRecommendations.
C. Structured journal reflection: generateJournalAnalysis.
They differ in prompt, context, temperature, output limit, validation, and fallback behavior.

Base system instruction:
The baseSystemInstruction template describes an emotional-support companion. It constrains topic scope, allows general educational discussion of mental-health concepts without diagnosis, prohibits prescriptions and promises of cures, treats user/profile/history/journal material as untrusted reference data, requires honest bounded memory, and asks for concise empathetic responses with at most one gentle follow-up question. It interpolates JSON.stringify(topicGroups) from backend/config/mentalHealthTopics.js. The source also contains crisis-resource wording; this guide explains its implementation without presenting those hardcoded contacts as freshly verified resource advice.

Chat-specific prompt construction:
  formattedHistory takes the last 10 sanitized messages.
  Stored role 'user' maps to provider role 'user'; stored 'ai' maps to 'model'.
  Each message becomes {role, parts:[{text:...}]}.
  A conversational extension permits greetings, small talk, hobbies, motivation, and wellbeing-related music conversation while retaining boundaries against code/homework and unsupported medical claims.
  It asks the model to vary responses, avoid exercises the user declined, and not claim human feelings or invented memories.
  A profile/memory extension includes the sanitized known name or 'unavailable'.
  It explicitly tells chat not to advertise the wellness exercise catalog in replies.
  The current user content is JSON.stringify of currentMessage, conversationalIntent, earlierUserExcerpts, and consentedWellnessContext.
  requestGemini calls getAIClient().models.generateContent with model, contents, and config.
  Chat config uses systemInstruction, temperature:0.65, maxOutputTokens:800.

Temperature is a sampling setting affecting variability, not an accuracy percentage. maxOutputTokens is a provider output budget, not a word count or guaranteed length.

Chat response selection in generateChatResponse:
  Validate input -> sanitize history -> detectChatIntent.
  Safety interception -> return a predefined safety response.
  Unrelated task -> return SCOPE_REPLY.
  Plain greeting -> greetingReply, selected locally from alternatives.
  Name question -> answer from buildMemory when available, otherwise acknowledge missing information.
  AI_MODE==='mock' -> return fixed mock supportive text.
  Otherwise -> generate with Gemini -> validate output -> return source:'gemini'.
  Failure -> return source:'unavailable'; route converts it into HTTP 503.

invalidChatOutput rejects empty output, non-string output, text above 5000 characters, several code/script/SQL patterns, and patterns resembling medication dosage instructions. This is a heuristic guard, not a proof that every unsafe sentence will be detected.

Recommendation prompt:
  Receives bounded context and a catalog containing id/title/description/duration/suitableFor.
  Asks for a 2-4 sentence reflection and 1-3 suitable exercises strictly from the catalog.
  Requires JSON with reflection and recommendations:[{id,reason}].
  Uses temperature:0.5, maxOutputTokens:1000, responseMimeType:'application/json'.
  JSON.parse parses response.text. The code filters recommendations to real IDs and string reasons, limits to three, trims reasons to 200 characters, and caps reflection length.
  If no valid catalog choices remain, it throws so the route can use rule-based recommendations.

Journal prompt:
  Includes the current title and full entry body plus catalog IDs, titles, and durations.
  Asks for emotionalPatterns, stressTriggers, positiveDevelopments, recurringConcerns, and at most one recommendedExercise.
  Requires JSON and uses temperature:0.5 with maxOutputTokens:1000.
  It validates the exercise ID against the catalog and constructs a local /wellness?activity= URL.
  A malformed JSON response throws; the calling route decides whether to save without analysis or return an analysis error.

Retry and timeout behavior:
  createGeminiRequest accepts an injected generate function (useful for testing), wait function, and random function.
  It tries at most three times, adding AbortSignal.timeout(10000) to each generation config.
  Only provider statuses 500, 502, 503, and 504 retry.
  Delay is 500*(2**attempt)+random jitter of 0-199 ms: roughly half a second, then one second.
  Authentication, validation, and quota errors do not retry through this wrapper.
  The SDK client also has httpOptions timeout 10000 and retryOptions attempts:1, so the project controls retry policy in its own wrapper.
  Retry does not mean every request succeeds; callers still have fallback/error branches.

12. MEMORY, PERSONALIZATION, AND CONSENT
=======================================
Sources: backend/services/chatMemoryService.js and moodContextService.js.

There are two different context sources:
  Current-conversation history: read from the authenticated conversation to maintain continuity.
  Broader personal context: other conversations, moods, check-ins, and eligible journals, fetched only according to consent.
Turning off broader context does not erase the current conversation or stop the model from receiving the current message.

sanitizeHistory:
  Accepts only user/ai role records with string text.
  Removes out-of-scope responses and their associated preceding user prompts.
  Considers up to the last 20 messages, with an overall 18,000-character budget and up to 3000 characters per selected message.
  Removes control characters and carries relevant safety flags.
  The later Gemini formatting stage uses the last 10 of these sanitized messages.

buildMemory:
  Filters prior user messages to relevant scope.
  Looks for bounded earlier excerpts such as preferences, 'just listen', name statements, or relevant personal details.
  Keeps at most six selected earlier excerpts, each capped at 220 characters.
  safeName permits a bounded name composed of suitable Unicode letters/marks, spaces, apostrophes, and hyphens.
  A stated name in conversation can override the account name in this prompt memory.
  Broader wellness context is included only when contextConsent===true.
  This is bounded prompt construction. It is not a continually trained personal model or unlimited long-term recall.

getMoodContext uses a 30-day cutoff and ownership filters:
Moods, if includeMoods:
  Read up to seven recent non-synthetic mood records.
  Fetch their completed non-synthetic MoodCheckins.
  Assemble score, label, emotions, a short note, and up to six non-empty question answers.
Other chats, if includeChats:
  Read up to three recent non-synthetic conversations, excluding the current conversation when its ID is supplied.
  Read the most recent three user messages from each, capped at 300 characters.
  Use Mongoose documents rather than lean() here so encrypted title/text getters run.
Journals, if includeJournals:
  Read up to three recent non-synthetic entries that ALSO have allowAIAnalysis:true.
  Build short title/mood/body snippets and some saved analysis fields.
  sanitizeWellnessContext later retains its supported subset; not every field initially assembled by getMoodContext is sent to Gemini.

Consent by workflow:
  Chat checkbox starts false and its true value permits the chat route to request moods, chats, and eligible journals.
  Wellness recommendation UI starts with moods/chats selected but sends data only when the user initiates the request. It explicitly sends includeJournals:false.
  The recommendation API also supports a validated consent object, or true as a shorthand for moods/chats and no journals.
  Individual journals must have their own analysis opt-in before they can enter broader journal context.
  Saving a journal without analysis does not call Gemini for that entry through the creation branch.

Source labels such as recentChatThemes do not prove a separate semantic summarizer ran. This service primarily assembles truncated user excerpts. Context is retrieval of ordinary documents by ownership/date, not vector similarity search or embedding-based RAG.

13. SAFETY AND SCOPE ROUTING
===========================
Sources: backend/services/safetyService.js, scopeService.js, chatIntentService.js; backend/config/mentalHealthTopics.js.

normalize performs Unicode normalization, punctuation normalization, whitespace compression, and lowercasing. matchesTopic checks vocabulary terms against normalized text. topicGroups covers emotional concerns, conditions, therapy terminology, wellness, safety, and product concepts. Inclusion of a term such as mood forecasting is not an implemented forecasting feature.

checkMessageSafety:
  Uses regular-expression rules and recent conversation flags.
  Distinguishes some educational/historical/negated discussion from current risk language.
  Looks at the latest AI safety question so a short follow-up can be interpreted in context.
  Returns category, level, requiresSafetyHandling, isCrisis, intercept, and reply, sometimes awaitingSafetyCheck.
  Categories include immediate danger, self-harm, abuse, acute distress, educational safety support, and none.
  An intercept supplies predefined guidance without relying on model generation.

checkTopicScope:
  First rejects explicit unrelated requests such as code, homework solving, calculations, or attempts to reveal secrets/instructions.
  conversationalIntent detects whole-message greetings, music, motivation, and casual conversation.
  Otherwise it checks mental-health vocabulary, supportive language, simple conversation phrases, memory requests, personal statements, and some short follow-ups with relevant history.
  Whole-message greeting matching prevents 'Hello, now write code' from automatically receiving a greeting-only route.

detectChatIntent calls safety first, then scope. greetingReply and variedReply choose local variants using randomInt. They avoid recently repeated AI wording where alternatives exist.

safetyFromContext inspects separate notes/excerpts instead of concatenating them into one big string, so a historical/negated statement in one record cannot as easily suppress an urgent statement in a different record. Recommendations check this before using cached analysis.

These mechanisms are programmatic safeguards. They are not a clinically validated risk model, do not contact emergency services, and can miss wording outside the patterns. Crisis.jsx is a resource page with links; it is not a dispatch integration. This documentation does not verify the current availability of its hardcoded external resources.

14. WELLNESS ACTIVITIES AND RECOMMENDATIONS
==========================================
Files: frontend/src/pages/Wellness.jsx; shared/wellnessCatalog.json; backend/services/wellnessService.js; backend/services/recommendationService.js; backend/routes/recommendationRoutes.js; backend/routes/wellnessRoutes.js.

The eight exercise IDs and titles are:
  breath - Guided Breathing; box - Box Breathing; sleep - Sleep Ritual;
  scan - Body Scan; gratitude - Gratitude Pause; morning - Morning Intention;
  ground - 5-4-3-2-1 Grounding; movement - Gentle Movement Break.

The backend wellnessService imports shared/wellnessCatalog.json and returns activities, looks up an ID, or maps a mood score to activity IDs. The frontend currently defines a similar activities array locally, including icons and step instructions. Therefore the project does not yet use one single runtime catalog definition for both browser and server; matching IDs connect the two lists.

Ordinary browsing:
1. Search text and selected category are state.
2. useMemo filters activities by category and title/description substring.
3. openActivity opens an activity panel and resets exerciseMode to 'read'.
4. ?activity=ground selects the matching known local activity on navigation.
5. closeActivity clears state and removes the activity query parameter.
6. Readable steps and optional embedded videos are offered.

BreathingTimer:
  Holds minutes, elapsed, and running in state. Options are 2, 3, or 5 minutes.
  A setInterval increments elapsed once a second; effect cleanup clears the interval.
  elapsed % 10 < 4 selects an inhale phase, giving a four-second inhale portion and six-second exhale portion of the displayed cycle.
  CSS classes animate circle size. Play/Pause toggles running; resetTimer clears progress.
  Reaching total stops the timer. This timer does not itself save a completed-session record to Atlas.

Video behavior:
  guidedVideos maps activity IDs to hardcoded YouTube IDs.
  Videos use youtube-nocookie.com embed URLs and links to watch on YouTube.
  This is an embedded external player, not the YouTube Data API, AI-generated video, or automatic video search.
  The standalone guidedVideo is ucla-mindfulness.
  submitFeedback sends that activityId and helpfulness to POST /api/wellness/sessions.
  Only ucla-mindfulness is accepted by the model/route, with helped, neutral, or not_helpful.
  Do not describe all eight exercises as having database completion tracking.

Personalized recommendation workflow:
1. Click the recommendation action in Wellness.
2. getAIRecommendations requires at least one selected source and a token.
3. POST /api/recommendations carries the consent object and optional refresh flag.
4. normalizeConsent rejects invalid/non-boolean permission values and requires at least one allowed source.
5. getMoodContext retrieves only permitted records.
6. safetyFromContext runs before cached output is considered.
7. recommendationCacheKey hashes the consent and actual context, prefixed with user ID/version.
8. A valid cached result is returned with fromCache:true unless refresh===true.
9. getPersonalizedRecommendations builds a rule-based fallback.
10. If there are no context entries, default catalog suggestions return without a model call.
11. In mock mode, the endpoint returns rule-based suggestions with source:'rules'.
12. Otherwise generateMoodRecommendations asks Gemini for bounded catalog choices.
13. The route maps validated IDs back to canonical catalog metadata and local activity links.
14. It caches the response for 900 seconds and returns source:'gemini'.
15. Provider/validation failure returns source:'rules' and fallback wording rather than pretending Gemini succeeded.

Rule scoring in recommendationService:
  Combine the latest mood's emotion labels/note/answers, recent chat notes, and journal snippets into lowercase context text.
  Add 3 points for each matching suitableFor tag.
  Add 2 points for activity IDs preferred for the latest score.
  Sort by score, keep three, remove the internal score from the response.
  Reasons come from fixed strings for each activity category.
Example: a low score plus text containing stress can make breathing and grounding rank highly. That is explicit scoring logic, not learned weights.

The separate GET /api/wellness/recommendations returns up to three allowed category recommendations from the most recently completed MoodCheckin. It is not the same endpoint as POST /api/recommendations. The inspected Wellness page's personalized action uses the latter.

15. EVENTS, ENROLLMENT, AND PAYMENTS
===================================
Files: frontend/src/pages/Events.jsx; frontend/src/lib/eventsApi.js; backend/routes/eventRoutes.js; backend/services/eventStore.js; backend/services/eventPayments.js.

All Events calls use the main API:
  CORE_API = VITE_API_URL or http://localhost:5000, without trailing slash.
  EVENTS_API = CORE_API + '/api/events'.
Events uses existing Atlas events and enrollments collections through the native collection interface exposed by the shared Mongoose connection. There is no Event.js Mongoose model in this implementation.

Discovery:
1. Events tracks search, category, format, sort, price, date range, page, and reload state.
2. A useEffect debounces listing requests by 180 ms.
3. URLSearchParams contains q, sort, page, limit=12, and optional filters.
4. Browser date selections become timestamp boundaries: from starts the first local day; to is the next day after the selected final day, making the upper bound exclusive.
5. Backend validates date ranges and free/paid filter values.
6. store.events reads published:true records.
7. The route filters events whose endsAt is still in the future, applies text/category/format/date/price conditions, sorts, and slices for pagination.
8. publicEvent computes spotsRemaining and paymentAvailable and excludes private meeting links.
9. AbortController cleanup prevents obsolete requests from replacing current results.

Scalability detail: the current store fetches all published events and the route filters/paginates in JavaScript. It does not execute all search/sort/pagination operations as a MongoDB aggregation or indexed query. This becomes more expensive as the catalog grows.

Schema adaptation:
  Atlas _id ObjectId -> JSON string _id.
  host.name -> frontend host string.
  In-person -> frontend 'In person'.
  meetingUrl -> internal joinUrl, selectively exposed after access checks.
  sampleContent -> isDemo.
  Structured agenda entries -> strings assembled from time/title/description.
  user/event ObjectIds in enrollments -> userId/eventId internal strings.
  gatewayOrderId/gatewayPaymentId -> orderId/paymentId.
  holdExpiresAt -> holdUntil.
This is read-time adaptation; it does not rewrite old events to match a new schema.

Details and UI:
  openDetails stores the slug in ?event=...; a request can load a shared deep link.
  startEnrollment redirects unsigned users to sign-in with an Events return path.
  Dialog components show details, confirmation, and cancellation.
  busy.current prevents repeated UI actions; refs preserve focus and checkout state.
  auth-change/storage/focus listeners react to token changes.
  requestJson has a 25-second timeout and combines an external abort signal when supplied. On a matching-session 401 it clears login storage and dispatches auth-change.

Free enrollment:
1. POST /api/events/:id/enroll verifies authentication, visibility, start time, capacity, and applicable limits.
2. Existing confirmed enrollment is returned rather than duplicated.
3. A pending refund request blocks rebooking.
4. store.transaction starts a MongoDB session and transaction.
5. It increments the event's __v within that transaction. Concurrent seat allocation for the same event contends on this document, allowing transaction retry rather than independent successful last-seat allocations.
6. It re-reads the existing enrollment and counts occupied seats.
7. A confirmed booking or unexpired pending hold occupies a seat; an expired/cancelled hold does not.
8. It creates/reuses an enrollment ID and reference, with status:'confirmed' and paymentStatus:'not_required'.
9. save uses updateOne with upsert, $set for booking state, and $setOnInsert for initial fields.
10. The transaction recomputes confirmed enrolledCount and commits.
11. The browser updates My events from the returned enrollment.

Native unique indexes observed in Atlas enforce one enrollment per {user,event} and a unique reference. Idempotency also comes from application checks. The existing document is updated in place for intended booking-state changes rather than copied to a second collection.

Paid checkout:
1. Paid events require both Razorpay key variables. They are absent in the inspected configuration, so paid booking is currently disabled and free booking still works.
2. With credentials, the enrollment starts pending with paymentStatus:'pending' and a 15-minute hold.
3. claimOrder conditionally sets orderRequestUntil for 60 seconds so competing backend requests do not create duplicate orders at the same time.
4. createOrder POSTs to Razorpay orders with amount in paise, currency INR, and the booking reference as receipt.
5. Backend attaches the returned order ID after re-reading the booking within a transaction, preserving cancellation that occurred while the provider request was pending.
6. Frontend loads https://checkout.razorpay.com/v1/checkout.js and creates window.Razorpay using server-issued checkout details.
7. flushSync closes the application dialog before external checkout opens, avoiding overlapping dialog/focus problems.
8. Checkout success sends payment identifiers/signature to /verify-payment. It does not directly mark the booking paid in MongoDB.
9. verify checks that the supplied order is the stored order, computes HMAC-SHA256 of orderId|paymentId using the backend secret, and compares signatures with timingSafeEqual.
10. Backend fetches the payment from Razorpay, then requires captured status, matching order ID, expected amount, and INR currency.
11. confirmPayment rechecks capacity and event start time transactionally.
12. A valid available booking becomes confirmed/paid. A late payment without a usable place becomes cancelled/refund_requested.

Amounts are integer paise: 15000 paise means 150 rupees. Integer minor units avoid common decimal rounding mistakes. Existing Atlas fields such as feeBps are not automatically used to add fees by the inspected order-creation function.

Reconciliation and cancellation:
  GET /mine checks pending orders with the provider when payments are enabled, recovering missed browser callbacks.
  Cancellation clears the hold. A paid booking records refund_requested; it does not issue a provider refund.
  A payment captured after cancellation must not restore access; it records a refund request.
  Cancellation after the event starts is rejected.
  An order-creation failure releases a reservation where appropriate.
  There is no webhook endpoint or scheduled worker in this module. Reconciliation currently depends on requests such as My events refresh.

Meeting access:
  Only a confirmed enrollment with paid or not_required payment status can expose an online join link, and only before the event ends.
  Public responses, pending/cancelled bookings, and in-person events do not receive the link.

Calendar and sharing:
  downloadCalendar constructs iCalendar (.ics) text in the browser, escapes text, creates a Blob URL, triggers an anchor download, and revokes the URL.
  It is a file export, not Google Calendar API synchronization.
  copyEvent writes a public deep link with navigator.clipboard; it does not share private meeting URLs.

Mongoose versus native collection operations:
  Most modules use Model.find/create/save, gaining schema casting, validators, hooks,
  timestamps, and getters.
  Events uses connection.db.collection directly, avoiding a schema rewrite and preserving
  the existing field layout. Native operations do not automatically run Mongoose
  validation/hooks; the route and adapter must implement their rules deliberately.

Relationships are references, not SQL joins:
  A journal belongs to a user through user:ObjectId.
  A questionnaire belongs to a mood and a user.
  An enrollment relates a user and event.
  Conversation messages are embedded inside the conversation document.
There are no automatic foreign-key cascades from declaring ref:'User'. Deleting a mood
in moodRoutes does not also delete its MoodCheckin in the inspected handler.

Why indexes matter:
An index is a search structure MongoDB maintains to locate records efficiently. A unique
index also rejects duplicate indexed keys. A non-unique index can accelerate finding a
user's date but does not enforce one record per date. unique:true is a database constraint,
not a substitute for every validation or user-friendly duplicate error.

Common database operations:
  findOne({email}) reads one matching user.
  find({user}).sort({createdAt:-1}) reads the owner's newest records first.
  select(...) projects only needed fields. limit(7) bounds a context read.
  lean() returns plain objects without normal document getters/methods; avoid it when
  code relies on chat decryption getters.
  create({...}) inserts and validates a model document.
  new Model({...}); save() builds then persists a document.
  findOneAndUpdate(filter,update,{returnDocument:'after',runValidators:true}) atomically
  changes a matching record and returns its new representation.
  $set changes listed fields; $unset removes a field; $inc increments a number;
  $setOnInsert runs only for the inserted portion of an upsert.
  $in matches one of a list; $ne excludes a value; $gte/$gt/$lte compare boundaries;
  $or allows alternative matching conditions.
  countDocuments counts matches, used for users and occupied event seats.
  findOneAndDelete deletes the owned document matching a filter.
  withTransaction groups capacity checks and state changes with a session.

17. ENCRYPTION AND OTHER SECURITY BOUNDARIES
==========================================
backend/services/chatEncryptionService.js implements field encryption using Node's
built-in crypto module rather than a third-party encryption package.

getEncryptionKey requires CHAT_ENCRYPTION_KEY to be a canonical base64-encoded 32-byte
key. Missing/invalid keys fail startup. This key is distinct from JWT_SECRET,
GEMINI_API_KEY, and Razorpay credentials because each has a different purpose.

encryptChatText generates a fresh random 12-byte IV, uses aes-256-gcm with a 16-byte
authentication tag, and sets additional authenticated data including field purpose and
version. It encrypts UTF-8 text and stores tfenc:v1: plus encoded IV/tag/ciphertext.
Different IVs make equal plaintexts produce different encrypted outputs. The tag detects
tampering. Purpose-bound authenticated data prevents treating an encrypted title as a
valid encrypted message field without detection.

decryptChatText parses/checks the envelope, sets the expected tag/AAD, and returns
plaintext only after authenticated decryption succeeds. Legacy plaintext is readable for
migration compatibility. Failures do not return unauthenticated partial plaintext.

encryptedString returns Mongoose field options:
  setter -> encrypt new assignments;
  getter -> decrypt reads;
  validator -> validate plaintext length after decryption.
Conversation JSON serialization enables getters, allowing an authenticated browser to
receive readable content while MongoDB holds ciphertext. Legacy-field pre-validate and
pre-save hooks encrypt still-plaintext fields when saved.

Encrypted by this application: conversation titles, message text, and stored recommended
exercise title/reason/URL.
Not encrypted by this mechanism: user IDs, timestamps, roles, safety flags, moods,
journal bodies, Events data. Password hashes are separate one-way protection.

This is server-side encryption of selected stored fields, not end-to-end encryption.
The backend can decrypt messages and sends authorized plaintext context to Gemini when
needed. Local development uses HTTP; source code alone does not prove production HTTPS,
Atlas backup policy, or deployment network security.

Other boundaries:
  Ownership filters tie personal requests to the caller.
  CORS controls browser cross-origin response access, not all non-browser callers.
  Prompt instructions alone are not complete prompt-injection protection.
  The Markdown component does not inject arbitrary HTML.
  Events verify provider signatures server-side; browser callbacks are untrusted.
  Provider keys remain in backend environment variables.

Status codes in practice:
  200 successful read/update/action; 201 creation; 400 malformed/invalid input;
  401 missing/invalid login; 403 consent/origin refusal where checked;
  404 missing/unowned record; 405 unsupported event method;
  409 conflict, full event, already-completed check-in, or concurrent update;
  429 request limit; 500 internal failure; 502 payment-provider failure;
  503 unavailable chat generation or disabled paid enrollment.
Different modules have different validation/error detail. Not every malformed ObjectId
or JSON parser error is normalized into one uniform JSON error response.

19. JAVASCRIPT, REACT, AND DATABASE FUNCTIONS EXPLAINED
=====================================================
An import supplies names from another module; it does not call every imported function.
For example, importing generateChatResponse allows a route to call it later when a
request arrives. Requiring a module can execute its top-level setup once per process.

CommonJS vs ES modules:
  backend/package.json has type:'commonjs'; backend files use require/module.exports.
  frontend/package.json has type:'module'; frontend files use import/export.
  Named import: import {useState} from 'react' takes a particular exported name.
  Default import: import Chat from '../pages/Chat' names the default export locally.
  Destructuring require: const {GoogleGenAI}=require('@google/genai') selects a property.
  Relative imports resolve project files. Bare names resolve packages. node:crypto is
  a built-in Node module; it does not need a separate dependency installation.

React hooks in actual use:
  useState: remembers mutable view data such as Journal.body or Events.page.
  useEffect: starts loading, listens to auth changes, or runs timers after rendering;
             its cleanup removes listeners/intervals and aborts obsolete requests.
  useMemo: caches a calculation for its dependency values, such as weekly chartData.
           It does not persist that result to MongoDB.
  useCallback: stabilizes a function identity, such as Dashboard.loadCore or Events.loadMine,
               so dependent effects do not restart merely because a new function was allocated.
  useRef: holds a mutable value without triggering a render, such as sendingRef,
          a DOM scroll target, checkout instance, or the questionnaire's save queue.
  useNavigate: changes the browser's React route programmatically.
  useLocation: reads current path and navigation state, including sign-in return paths.
  useSearchParams: reads/writes ?event=, ?tab=, or ?activity= in the URL.
  flushSync: forces relevant UI updates to commit before opening external checkout.

Why handlers call preventDefault:
HTML forms normally navigate/reload on submission. SignIn prevents that so JavaScript
can send fetch, display errors, store the token, and navigate deliberately.

Controlled input:
  value={body} onChange={event=>setBody(event.target.value)}
The value on screen follows state; typing produces an event that updates state.

Immutable state updates:
  setEntries(previous=>[newEntry,...previous.filter(...)])
This makes a new array, replaces a record by ID/date, and gives React a changed reference.
It does not directly edit MongoDB; that requires the corresponding successful request.

Frequently used language tools:
  map transforms each item (documents into response DTOs or JSX list items).
  filter keeps only matching items (owner's visible status or matching search).
  find returns the first match (catalog ID, today's entry).
  some checks if any item matches (valid catalog recommendation).
  reduce accumulates values (sum mood scores).
  sort orders values (newest timestamps or event start dates).
  slice selects bounded history/page/context portions.
  Set deduplicates values (ranked categories or recorded dates).
  Map associates keys with values (date->mood or mood ID->check-in).
  Object.fromEntries turns answer pairs into an object for easy rule lookup.
  Spread (...) copies/merges objects or arrays; later fields override earlier fields.
  Optional chaining (?.) handles possibly missing nested data.
  Nullish coalescing (??) replaces only null/undefined, useful where zero is meaningful.
  A strict equality check (=== true) avoids accepting a truthy string as consent.
  Template literals build URLs and readable strings using ${...} placeholders.
  encodeURIComponent protects an ID/slug used inside a URL segment/query value.
  Date/Date.parse compare event boundaries; toISOString uses a UTC representation.
  JSON.stringify/parse convert between object values and JSON text.

Asynchronous reasoning:
  await pauses that async function until its promise settles; other requests can run.
  try/catch handles rejected promises and thrown errors. finally resets loading states
  or closes sessions even after failure.
  Promise.all overlaps independent work but rejects if one operation rejects.
  Promise.allSettled reports each result independently, used by Dashboard.
  AbortController can stop waiting for an obsolete fetch. It is not a database rollback.
  A Promise queue orders operations within one process/component, not every process.

Express basics:
  req.params contains path parameters such as :id.
  req.body contains JSON parsed by express.json().
  req.headers contains Authorization and other headers.
  next() lets middleware pass control to the next handler.
  res.status(201).json({...}) sets HTTP status and serializes response JSON.
  app.use('/api/moods',router) prefixes the router's local paths.

Advanced event helpers:
  AsyncLocalStorage in eventStore is Node's asynchronous-context storage. It associates
  database operations with the current transaction session. It is unrelated to browser
  localStorage despite a similar name.
  context.run(session,callback) makes the session available within that async chain.
  options() adds {session} only when one is active.
  ObjectId.isValid/new ObjectId adapt string request IDs to native MongoDB IDs.
  randomUUID generates a booking reference; it is not the MongoDB transaction ID.
  timingSafeEqual compares equal-length signature buffers without early per-character exit.
  createHash computes content fingerprints; createHmac computes a keyed signature.

21. ADVANCED CONSISTENCY, FAILURES, AND LIMITATIONS
==================================================
Concurrency means several requests can act on the same resource at once.

Conversation consistency:
  optimisticConcurrency:true uses a version to detect a stale document save.
  A VersionError becomes 409 with a reload/retry message instead of silently accepting
  a conflicting append. Rename deliberately increments __v too.

Journal consistency:
  The analysis update filters on title/body/updatedAt as well as owner and ID.
  If the entry changed during the slow external call, saving stale analysis fails safely.

Questionnaire consistency:
  A browser-side Promise queue orders saves from that component.
  A unique user/moodEntry index prevents two logical check-in documents.
  This does not mean all edits from multiple devices are globally serialized by that queue.

Event consistency:
  Transactions and an event-document write serialize seat decisions across routers.
  The unique enrollment key prevents duplicate user/event bookings.
  A short checkout lease coordinates external order creation.
  Network calls to a payment provider are not part of a MongoDB atomic transaction.
  A process crash after provider order creation but before local persistence can still
  require operational reconciliation. The lease is not a mathematically exact-once
  distributed transaction between Atlas and Razorpay.

Cache behavior:
  MemoryCache has a Map of values and expiry timestamps.
  get deletes an expired item when accessed; set defaults to 900 seconds.
  Different processes have separate caches; restarting loses cached values.
  It is not Redis and has no shared background eviction worker.
  Consent/context hashes prevent using recommendations from a different selected source
  set or changed source content. A refresh flag deliberately bypasses reuse.

Current implementation limits verified from code:
  No account password-reset backend, email-verification workflow, profile settings CRUD,
  token refresh/revocation service, therapist booking module, or admin dashboard routes.
  Signup accepts a request-supplied role; the UI's client value is not a server role policy.
  Registration goals are not persisted.
  Dashboard and Mood use inconsistent labels for some numeric scores.
  Mood daily uniqueness is not enforced by a unique index; date/ID validation is uneven.
  Deleting a parent record does not automatically cascade through related collections.
  Most personal history endpoints load lists without pagination; Events pagination happens
  after loading published events into server memory.
  Embedded chat messages grow within a single conversation document; the code does not
  introduce archival or a separate message collection for unlimited history.
  Journal creation-time analysis has different prechecks from /:id/analyze.
  Journal detail consent and Wellness source checkboxes initially default true, although
  backend calls still require the explicit request flags. Chat broader-context consent defaults false.
  Questionnaire category IDs and exercise IDs are not a single uniform namespace.
  The same catalog content is duplicated in Wellness.jsx and shared JSON.
  Events payment credentials are absent in the inspected environment. Refund requests
  are stored states, not automated refund payouts; no webhook or payment worker exists.
  The generic Markdown link parser does not itself enforce allowed URL protocols.
  Backend CORS is hardcoded to the local frontend origin, so deployment must account for it.

Informational page boundaries:
  Careers.jsx displays predefined roles and a mailto link, not application submission CRUD.
  Press.jsx displays hardcoded coverage/funding text and contact UI. Source text does not
  establish that those external coverage claims are factual; there is no news-fetch API.
  Cookies.jsx changes preferences in component state; no persistent cookie-consent backend
  or browser storage write is implemented by those toggles.
  Privacy.jsx and Terms.jsx render policy text; text mentioning a capability does not
  create corresponding export/deletion/security functionality.
  Crisis.jsx contains predefined resources and links; its /self-care link has no matching
  registered route in routes.js and therefore reaches NotFound.
  NotFound.jsx is the fallback route with navigation back into the app.

A conceptual worked example (fictional input, not a private database record):
A student signs in, records mood score 2 with note 'I feel pressure about an exam', and
opts into a questionnaire. Saving the score writes a Mood; saving questionnaire answers
writes a linked MoodCheckin. Asking Wellness for recommendations with moods enabled
retrieves those records, checks safety, and either uses cached output, Gemini, or rule
scoring. Clicking a returned ground exercise opens /wellness?activity=ground. Starting a
breathing timer is local UI work. Writing a journal with analysis disabled saves the
journal without that optional AI call. Later enabling chat context allows relevant
bounded information to be included in a chat request; it does not grant arbitrary access
to every record or train a private model.

To diagnose a failed request without changing code:
  Inspect browser Network for URL, HTTP method, status, request payload, and response.
  Confirm VITE_API_URL points to the main backend port.
  Confirm a Bearer token is present for protected endpoints.
  Find the exact route and ownership filter; distinguish 401 from 404 or 409.
  Check server configuration names without exposing secret values.
  Distinguish a Gemini failure from a database failure and from a local UI-state issue.
  For Events, a confirmed display should come from a verified backend response rather
  than merely receiving the Razorpay browser callback.

24C. IMPORTANT BUILT-IN AND PLATFORM FACILITIES
-----------------------------------------------
node:crypto: encryption, random bytes/IDs, SHA-256 fingerprints, HMAC, timing-safe comparison.
node:async_hooks: AsyncLocalStorage transaction-session context.
node:fs: administrative file reads/writes; not browser filesystem access.
node:path: resolves script/config paths independently of current directory.
node:child_process: verification scripts launch a temporary server.
node:http: tests can wrap Express in an HTTP server on a temporary port.
node:test and node:assert/strict: regression runner and assertions, without a Jest dependency.
Browser fetch/AbortController: request/response and cancellation.
Browser localStorage: token/profile persistence, not MongoDB storage.
Browser Clipboard/Blob/URL: public-link copy and calendar file export.
URLSearchParams: safe query-string construction.
setTimeout/setInterval: debounce, timeout, breathing timer; cleanup prevents stale work.
